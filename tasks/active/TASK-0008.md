## Runtime orchestration contract

1. After configuration load at application session startup, capture an actual session-start instant and call `openAlarmSession(alarms, sessionStart)`. Apply its `nextAlarms`: remove once alarms at/before the session start without retroactive delivery; retain daily and future once alarms. Persist stale removal only if actual stale alarms existed, through the existing Config V3 adapter/protected persistence path. Do not eagerly rewrite a loaded V1/V2 document merely from migration. Preserve unsupported future documents and storage-failure feedback.
2. Instantiate `createAlarmEvaluator()` exactly once per mounted/open runtime session and retain it. Repeating production calls must use its `evaluate` method, not stateless `evaluateAlarms()`. Its 128-entry cache stays ephemeral, never Config or persisted state.
3. Prefer one central `evaluateAt(actualNow)` reading the latest alarms and city-zone map. Use actual `(previousActualInstant, currentActualInstant]`; the previous baseline begins at session start. Reuse the display ticker as an execution opportunity, without relying on nominal one-second punctuality. Route visible `visibilitychange`/foreground opportunity through the same function as a supplemental trigger, not another alarm engine.
4. After every successful domain evaluation, apply its configuration transition and advance the baseline to actual current time. Commit domain consumption/baseline before awaiting audio so asynchronous or failed playback cannot duplicate, block, or replay due processing. Persist only actual one-time consumption; retain the existing graceful storage failure/unsupported-version protection.
5. If `current < previous`, reset the baseline to actual current, emit nothing for that reversed interval, and resume ordinary evaluation afterward. Do not throw through the UI or synthesize occurrences. Add deterministic evidence. The evaluator cache is occurrence-resolution state, not delivery history.
6. Preserve every returned due event. Once alarms emit once, are removed and consumption is persisted; daily alarms remain. A long interval crossing several daily occurrences yields at most one due event per alarm, with no historical burst. Several different due alarms must all remain observable and each receive a cue request.
7. Edits/removals affect subsequent evaluations without recreating the runtime/evaluator unnecessarily. Manage ticker/listener/audio cleanup on unmount; prevent late async outcomes from mutating disposed state or losing events. Keep ordinary clock/settings/city behavior functional.

## Native audio and UI contract

- Keep browser audio behind a small injected/testable adapter. Use native Web Audio and a short finite synthesized cue; no runtime asset, network request, or production library. Exact frequencies/durations are implementation choices, not new product requirements.
- Provide a visible user-operated control such as `Enable / test alarm sound`. Its gesture creates/resumes an audio context and attempts the real/representative cue. Only indicate success (for example `Alarm sound ready`) after observed running/cue behavior supports it. Readiness is session-only, not Config V3 or persisted AudioContext state.
- Use actual context/playback behavior and caught failures as truth. Do not require experimental `navigator.getAutoplayPolicy()`. Due-time behavior must recheck readiness; a prior successful test does not guarantee future permission or physical audibility.
- Request a finite cue for each due event. Unavailable Web Audio, suspended/nonresumable context, rejected resume, or cue failure produces visible recoverable sound-unavailable/blocked feedback without claiming sound delivery or breaking the app. A pending resume must not hold up domain evaluation or leave the UI indefinitely claiming success; choose a bounded recoverable adapter outcome during implementation.
- Due processing remains valid when audio fails. Do not re-fire the same domain occurrence every second because playback failed. A user may retry enable/test; do not automatically recreate consumed historical domain events.
- Maintain small accessible runtime notifications independent of Config. Each event exposes city name, due status, and observed audible success versus unavailable/blocked outcome. Prefer persistent-until-dismissed notifications; all simultaneous cities/events remain visible. Use suitable live status semantics, keyboard-operable controls, and useful focus behavior.
- Dismissal clears only the runtime notification; daily configuration remains, and once configuration is already consumed. Do not persist notifications across reload.
