- Status: ready
- Risk: medium
- Execution profile: cloud-standard
- Reasoning target: medium
- Required review: independent-cloud-standard
- Security impact: none
- Security rationale: Reorders existing browser-local city IDs through the existing Config V3 persistence path; no new data class, trust boundary, permission, network behavior, or deployment change.

## Goal

Let the user persistently reorder selected world-clock cards one position at a time with visible, keyboard-operable `Move earlier` and `Move later` controls.

## Non-goals

No drag-and-drop, browser-local clock reordering, Config V4 or migration, alarm redesign, or unrelated release acceptance. Do not add a production dependency or change architecture, workflow, deployment, trust boundaries, capabilities, public interfaces, or the stack/toolchain.

## Context

[FR-013 and FR-004](../../docs/product/requirements.md) approve manual ordering and persistence. The [M8 plan](../../docs/delivery/implementation-plan.md) is a single-human naturally linear increment with no DAG. Existing ordered `ConfigV3.selectedCityIds` is the canonical world-clock order; new cities already append to that array. Alarms are attached by city ID. Preserve the existing protected behavior for unsupported future configuration versions and browser-storage read/write failures. The released production baseline remains unchanged during this task.

## Acceptance criteria

- [ ] Each `Move earlier` / `Move later` action moves exactly the selected city clock by one position in the logical and rendered world-clock order; the browser-local clock remains outside that list.
- [ ] The first city clock's earlier control and last city clock's later control are disabled, including when only one city is selected.
- [ ] Controls are visible, keyboard-operable, and have accessible city-specific names that distinguish each action and city.
- [ ] Each successful reorder persists immediately through existing Config V3 `selectedCityIds`; reload and reopening in the same browser profile/context restore the chosen order.
- [ ] A city added after reordering appears at the end, and its addition persists without disturbing the chosen order.
- [ ] Reordering leaves every configured alarm attached to the same city, including after reload.
- [ ] Reorder attempts with an unsupported future stored configuration never overwrite its original storage bytes; existing in-tab behavior and warning remain intact.
- [ ] Browser-storage write failures leave the in-tab reorder usable and show existing save-failure feedback without claiming persistence; read/access failures retain existing fallback and warning behavior.
- [ ] World-clock controls remain usable and visually coherent in a representative narrow layout, without clipping or overflow caused by the new controls.
- [ ] No Config V4/migration, drag-and-drop, production dependency, architecture, workflow, deployment, trust-boundary, or capability change is introduced.
