## Goal

Add one global presentation preference (`digital | analog`) and one global digital time-format preference (`24h | 12h`), apply them consistently to the local clock and all selected world clocks, and persist them without losing existing selected-city configuration.

## Non-goals

- No alarm behavior from TASK-0007/TASK-0008.
- No city-catalog changes.
- No further city-picker redesign.
- No backend/runtime API.
- No router/store/UI framework.
- No new production dependency.
- No TASK-0009 final visual/release hardening.
- Do not replace the existing one-second shared `currentInstant` ticker with per-clock timers.
- Do not resolve or weaken the existing Playwright timing learning as part of this task.

## Context and defaults

TASK-0010 is integrated into `main`, hosted CI passed, and the product owner manually accepted the searchable city combobox.

The current persisted configuration is exact version 1 containing only ordered `selectedCityIds`.

FR-005 and FR-006 require global Digital/Analog and 12h/24h settings with persistence.

Backward-compatible defaults are:

- presentation mode: `digital`
- digital time format: `24h`

## Configuration migration contract

Introduce a new exact current configuration schema, preferably version 2, containing:

- ordered unique `selectedCityIds`;
- `presentationMode: "digital" | "analog"`;
- `timeFormat: "24h" | "12h"`.

Version 1 remains a supported migration input only.

Required behavior:

- A valid V1 document loads into the current in-memory configuration with all selected-city IDs and their order preserved.
- V1 migration supplies defaults `digital` + `24h`.
- Loading V1 alone must not eagerly rewrite browser storage.
- The migrated current-version document may be persisted on the next normal user configuration change.
- A valid current-version document restores all fields exactly.
- Current-version validation remains exact and rejects unknown extra fields, bad enum values, invalid/duplicate/non-catalog city IDs, and wrong field types.
- Malformed current-version documents recover to safe current-version defaults using the established invalid-data behavior.
- Future/unsupported versions retain the existing protection:
  - safe defaults in the current tab;
  - visible unsupported-version warning;
  - no overwrite of the future stored document when the user changes cities or presentation settings.
- Storage read/write failures remain graceful and visibly reported.

## Presentation contract

Expose visible, accessible global controls for:

- Digital / Analog
- 24-hour / 12-hour

Behavior:

- settings are global, not per-clock;
- they apply to the local clock and every world-clock card;
- Digital + 24h preserves current display semantics;
- Digital + 12h uses the same local/IANA civil time and visibly distinguishes AM/PM;
- Analog renders actual hour, minute, and second hands derived from each clock's civil time;
- local and world analog clocks use the same shared `currentInstant`;
- analog hand positions must respect each applicable local/IANA zone, including representative offset/DST behavior;
- the persisted 12h/24h preference does not change analog hand positions;
- returning to digital mode uses the previously chosen digital format;
- analog clocks retain an accessible textual representation of current civil time;
- city names, zone identity, remove controls, storage warnings, searchable combobox behavior, ordering, and duplicate prevention remain intact;
- styling should be coherent enough for functional review, while final visual polish remains TASK-0009.

A small framework-independent time/presentation helper or a small Vue clock-presenter component is allowed if it reduces duplication without creating a new architectural layer or dependency.

### Blocking finding R1 — medium severity, required before integration

`src/config.ts:72-73` classifies any present version other than numeric 1 or 2 as unsupported before schema validation. Thus otherwise current-shaped documents with `"version":"2"` or `"version":null` use future-document protection instead of invalid-data recovery. These values are malformed version fields, not evidence of a supported version discriminator for a future schema. This conflicts with the task's exact wrong-field-type validation and established invalid-data recovery contract.

Independent Node parser calls for both values returned `status: unsupported` and defaults. Independent built-app Chromium reproduction for both values showed the unsupported warning; changing presentation to Analog and format to 12h left the raw malformed document byte-identical, and reload reverted presentation to Digital. `App.vue`'s unsupported guard consequently prevents ordinary recovery writes indefinitely. `src/__tests__/config.spec.ts` currently explicitly expects unsupported for these values, so green tests encode the defect rather than prove the contract.

Required bounded remediation: validate the version discriminator's type/domain before applying unsupported-version protection. Malformed values (including string `"2"` and null) must produce invalid status, safe defaults, and the established visible invalid warning; the next normal configuration change must save valid V2 and survive reload. Preserve non-overwrite for legitimate unsupported numeric schema versions (including 3 and 99), lazy V1 migration, exact V2 validation, and all existing gates. Add contract-derived parser regressions and browser/component recovery-and-reload evidence for malformed version values. Do not broaden scope to alarms or rewrite unrelated persistence/UI logic. A fresh top-level finding-focused re-review must inspect the remediation and plausible persistence regressions.
