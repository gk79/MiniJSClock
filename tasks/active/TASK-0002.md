# TASK-0002: Add routine CI and manual GitHub Pages deployment path

* Status: ready
* Risk: high
* Execution profile: cloud-deep
* Reasoning target: high
* Required review: independent-cloud-deep
* Security impact: material
* Security rationale: This task changes GitHub Actions identities, workflow permissions, deployment mechanics, and the release trust path for GitHub Pages.
* Next handoff: independent-review
* Related requirements: NFR-003, NFR-007
* Related ADRs: ADR-002

## Goal

Materialize the approved GitHub delivery baseline so that routine pull-request/main CI executes the repository's canonical verification contract on a clean GitHub-hosted runner, and a separate human-triggered workflow can build a newly verified static artifact from `main` and deploy that exact artifact to GitHub Pages with least privilege.

## Non-goals

* Do not implement product features, city/time-zone behavior, persistence, presentation settings, or alarms.
* Do not automatically deploy on push, pull request, merge, schedule, or CI success.
* Do not trigger or authorize the first production release as part of implementation or review.
* Do not change the approved GitHub Pages hosting decision or `/MiniJSClock/` production base path.
* Do not introduce a PAT, repository secret, GitHub App credential, cloud credential, or other deployment secret.
* Do not use `configure-pages` automatic enablement or broaden permissions to make Pages setup work.
* Do not add Dependabot, CodeQL, SBOM generation, artifact attestation, third-party hosted security products, or unrelated repository protections.
* Do not upgrade the application/toolchain or approved GitHub Action pins merely because newer versions exist.
* Do not weaken `make ci`, `make security`, or another canonical Make gate to make hosted CI pass.

## Escalation triggers

* Trigger: any approved GitHub Action SHA/tag is unavailable, does not execute on the selected runner, or proves incompatible with another required action in the complete workflow.

* Required action/profile: stop, preserve evidence, and hand off to `chatgpt-analysis` for whole-workflow compatibility reassessment; do not silently upgrade one action.

* Trigger: Gitleaks 8.30.1 or OSV-Scanner 2.6.0 cannot be reproducibly provisioned from its official Linux x64/amd64 artifact with the approved checksum.

* Required action/profile: stop and hand off to `chatgpt-analysis`; do not use an unpinned installer, `curl | sh`, or a new wrapper Action.

* Trigger: `make ci` cannot pass on a clean `ubuntu-24.04` GitHub-hosted runner after exact Node/npm restore, approved security-tool provisioning, `make bootstrap`, and Playwright native dependency provisioning.

* Required action/profile: record the concrete incompatibility and escalate to `chatgpt-analysis`; do not weaken canonical gates.

* Trigger: Pages requires a PAT, repository secret, GitHub App credential, `contents: write`, `actions: write`, administration permission, or any permission beyond the approved Pages deployment model.

* Required action/profile: stop. Human/`chatgpt-analysis` must reassess platform setup or architecture.

* Trigger: GitHub Pages is unavailable for the repository/account or cannot be configured with Source = GitHub Actions.

* Required action/profile: stop before deployment verification and hand off to human/`chatgpt-analysis`; do not change hosting target autonomously.

* Trigger: implementation would deploy from a non-`main` ref or make deployment automatic.

* Required action/profile: stop; this violates ADR-002.

* Trigger: implementation or review would need to trigger an actual production deployment to prove task correctness.

* Required action/profile: do not deploy. Record the remaining production-runtime verification as release evidence requiring a later explicit human release verdict.

## Acceptance criteria

* [ ] Routine CI workflow exists and runs on pull requests targeting `main` and pushes to `main`.
* [ ] Routine CI uses explicit `ubuntu-24.04`, exact approved `actions/checkout` and `actions/setup-node` SHAs, and exact Node 24.21.0/npm 11.19.0 project metadata.
* [ ] Routine CI has no write permission; its effective repository permission is limited to `contents: read` unless a narrower/no-content step allows less.
* [ ] CI reproducibly provisions Gitleaks 8.30.1 and OSV-Scanner 2.6.0 from official release artifacts and verifies the approved SHA-256 values before putting the binaries on `PATH`.
* [ ] CI runs `make bootstrap`, provisions Chromium native Linux dependencies using the pinned project Playwright CLI, and then runs the unchanged canonical `make ci`.
* [ ] A real GitHub-hosted CI run for the TASK-0002 branch/PR passes the canonical `make ci` contract, including Gitleaks, OSV-Scanner, build, and Chromium E2E.
* [ ] A separate Pages workflow is triggered only by `workflow_dispatch`; push/PR/schedule triggers cannot deploy.
* [ ] The Pages workflow explicitly refuses/skips deployment unless `github.ref == 'refs/heads/main'`.
* [ ] The Pages build job uses explicit `ubuntu-24.04`, approved full-SHA Actions, exact project Node/npm restore, pinned security-tool provisioning, Playwright native dependency provisioning, and the unchanged `make ci` contract before Pages artifact upload.
* [ ] The Pages build job has only the permissions it needs: `contents: read` and `pages: read` for checkout/configuration of this private Pages repository.
* [ ] `actions/configure-pages` uses its normal read/configuration behavior only; automatic Pages enablement is not used.
* [ ] Only the generated `dist/` static output is uploaded through `actions/upload-pages-artifact`; source files, repository metadata, `node_modules`, test reports, and other workspace content are not included.
* [ ] The deploy job depends on the successful build/upload job and deploys that exact `github-pages` artifact rather than rebuilding.
* [ ] The deploy job uses the `github-pages` environment and only `pages: write` plus `id-token: write`; it does not require repository write access or secrets.
* [ ] Pages deployment concurrency prevents overlapping production deployments without cancelling an already-running production deployment.
* [ ] The workflow exposes the deployed `page_url` from `actions/deploy-pages`.
* [ ] Existing Vite `/MiniJSClock/` base-path behavior remains unchanged, and local/static artifact inspection confirms generated asset URLs are suitable for repository Pages hosting.
* [ ] No product/runtime dependencies or application behavior are changed.
* [ ] No actual production deployment is performed without a separate explicit human release verdict.

## Implementation notes

The implementation should prefer two explicit workflows:

1. routine CI for PRs/pushes, with read-only permissions and no Pages deployment authority;
2. manual Pages release workflow with a verified build job followed by a narrowly privileged deployment job.

Do not share deployment write permissions with routine CI.

The release workflow must build and verify the artifact in the same workflow run that uploads it; the deploy job consumes the uploaded artifact and must not rebuild application code.

Keep the existing local Make contract authoritative. GitHub Actions provisions the clean runner environment needed to execute that contract; it does not replace it with a parallel set of npm commands.

The Playwright native-dependency learning from TASK-0001 is deliberately applied here at the environment boundary. Do not silently promote or rewrite the learning candidate itself unless separately reviewed.

Version-sensitive compatibility is evaluated as a complete set: runner image + Action runtimes + Node/npm + package lock + Playwright browser/native libraries + security scanners + Pages permissions/artifact/deploy chain. A package/action being individually available is not sufficient evidence.
