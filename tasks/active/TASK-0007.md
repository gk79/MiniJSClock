## Goal

Implement the framework-independent city-local alarm domain, alarm configuration UI, and versioned browser-local persistence for one-time and daily alarms, ready for TASK-0008 to attach runtime overdue evaluation and audible delivery.

## Expected domain model

Prefer the smallest exact model satisfying the clarified requirements.

A reasonable V3 alarm representation is conceptually:

- one-time:
  - selected city ID;
  - recurrence discriminator `once`;
  - canonical resolved UTC instant;
- daily:
  - selected city ID;
  - recurrence discriminator `daily`;
  - exact city-local `HH:mm`.

There must be at most one alarm record per selected city ID.

Do not require a separate alarm identifier unless implementation evidence shows it is actually necessary.

## Persistence evolution

Evolve exact Config V2 to exact Config V3 containing alarms.

Required migration behavior:

- valid V1 -> in-memory V3:
  - preserve selected-city order;
  - default presentation Digital;
  - default format 24h;
  - alarms empty;
- valid V2 -> in-memory V3:
  - preserve selected cities;
  - preserve presentation;
  - preserve time format;
  - alarms empty;
- loading valid V1/V2 alone must not eagerly rewrite localStorage;
- next normal configuration change may persist exact V3;
- valid V3 round-trips exactly;
- alarm city references must correspond to selected city IDs;
- alarm city IDs must be unique;
- daily `HH:mm` must be exact and valid;
- one-time resolved instant must be canonical and valid according to the task's chosen exact representation;
- malformed current documents use invalid-data recovery;
- legitimate future numeric safe-integer versions greater than current V3 remain `unsupported` and protected from overwrite;
- preserve the TASK-0006 R1 discriminator rule: malformed version types/values are `invalid`, not `unsupported`;
- storage unavailable/write-failure recovery remains unchanged.

## Domain logic

Keep alarm semantics framework-independent TypeScript where practical.

Expected pure capabilities include:

- parse/validate city-local date and minute input;
- resolve one-time city-local date/minute to candidate instant(s) using the selected city's IANA zone;
- reject nonexistent civil minutes;
- deterministically handle repeated civil minutes according to the approved first-future rule;
- calculate the daily occurrence for a city-local date;
- skip nonexistent daily civil minutes;
- select only the first occurrence in repeated time;
- evaluate alarms over actual instant interval
  `(previousExclusive, nowInclusive]`;
- return due alarms/state transition deterministically without playing sound;
- consume one-time alarms after due;
- retain daily alarms;
- identify stale one-time alarms that predate a new application session without marking them due.

Use native `Intl` / IANA behavior and deterministic injected instants.

Do not add a time-zone library or Temporal/polyfill dependency unless the approved approach proves impossible; if a new dependency or consequential time architecture becomes necessary, stop and escalate.

## UI configuration

Provide visible accessible alarm configuration on selected world-clock cards.

At minimum support:

- Set alarm when none exists;
- recurrence choice: One-time / Daily;
- city-local time input;
- city-local date input for One-time;
- Save;
- Edit/replace the existing alarm;
- Remove alarm;
- visible concise alarm summary/state on the clock card;
- understandable validation for past/nonexistent one-time civil time.

The UI saves configuration only.

It must not emit an alarm or run due-alarm orchestration in TASK-0007.

Preserve:

- global Digital/Analog settings;
- 12h/24h display preference;
- existing city picker;
- city add/remove/order;
- one shared display ticker;
- existing storage warnings.

## DST / correctness test requirements

Deterministic pure tests must cover representative cases including:

- ordinary one-time resolution;
- one-time target in the past;
- New York spring-forward nonexistent local minute;
- New York fall-back repeated local minute:
  - before first occurrence;
  - between first and second occurrence where the second remains future;
- daily normal occurrence;
- daily spring-forward skipped occurrence;
- daily fall-back first-occurrence-only semantics;
- actual-interval overdue evaluation;
- no duplicate daily event from repeated hour;
- long delayed interval returns at most one due event per alarm;
- one-time consumption;
- daily retention;
- expired one-time on new-session boundary is not retroactively due;
- representative non-hour offset zone such as Asia/Kathmandu.

## Persistence/UI tests

Require tests for:

- V1 -> V3 lazy migration;
- V2 -> V3 lazy migration;
- exact V3 round-trip;
- malformed V3 recovery;
- future-version non-overwrite;
- TASK-0006 malformed-version discriminator behavior retained;
- alarm references/uniqueness validation;
- city removal also removes its alarm;
- alarm add/edit/remove persistence;
- reload restores alarm configuration;
- existing world-clock/settings configuration is preserved.

- native Intl/IANA cannot provide deterministic civil-time resolution with acceptable complexity;
- a new runtime time-zone/Temporal dependency appears necessary;
- requirements would need multiple alarms per clock;
- alarms need to survive city removal;
- local top-clock alarms become required;

- background/audio/autoplay mechanics become necessary to satisfy TASK-0007;
